# Frontend/backend gaps

The frontend calls only the existing `/api/v1` routes. The gaps below are not replaced with mock behavior.

| Feature | Missing capability | Required backend or configuration work | Frontend status |
|---|---|---|---|
| Secure authentication lifecycle | The API returns bearer tokens and has no refresh-token, secure-cookie, or logout endpoint. | Add a reviewed cookie/refresh/logout design if required. | Uses the API bearer token in tab-scoped `sessionStorage`; logout clears it locally. |
| Optician onboarding and store discovery | Registration creates a regular `USER`; there is no “my stores” endpoint. | Add a current-user stores endpoint if users need to manage multiple stores without saving an ID. | Store creation grants an active `PROPRIETAIRE` membership; owners and active opticians can manage their own optician profile. Store ID remains saved in the current browser session. |
| Draft store read | `GET /stores/:storeId` remains public and active-only. | None for the current single-store workflow. | Owners and managers read active or draft stores through authenticated `GET /stores/:storeId/manage`; the optician workspace uses this endpoint. |
| Store address display | Public store responses do not provide the address information expected by the explore page. | Add public store address/location fields or a safe public locations endpoint. | Store details show only fields returned by the existing API; no address is fabricated. |
| Payments and refunds | The frontend can read order payment/refund records, but there is no client payment initiation or refund request flow. | Configure and implement a payment provider; implement authorized payment/refund actions and document webhook verification. | Payment records are read-only; order checkout creates an unpaid order. No provider calls are simulated. |
| Virtual try-on files | Consent and session endpoints exist, but private upload/download, retention, and processing endpoints do not. | Implement private storage operations and access controls; configure `VIRTUAL_TRYON_CONSENT_VERSION`, `VIRTUAL_TRYON_CONSENT_PURPOSE`, and `VIRTUAL_TRYON_CONSENT_TEXT`. | Consent policy and session creation/listing are available; image upload and processing are explicitly absent. |
| AI recommendations and chatbot | No recommendation or conversation endpoints/provider integration is available. | Add reviewed API contracts and configure the chosen AI provider before implementing the assistant. | Backoffice displays a clearly marked Coming soon placeholder; it does not simulate answers or call an AI provider. |
| Stories | The required story model/API is not present in the current schema/API. | Propose and review schema changes separately, then add backend endpoints. | Not implemented. |
| Social media attachments | Text publications, comments, likes, and reposts are available, but there is no media upload/storage flow. | Add private/public media storage endpoints and authorization rules. | Text-based social interactions only. |
| Followed-store listing | Follow/unfollow actions exist, but there is no endpoint to list the authenticated user's followed stores. | Add a paginated, ownership-scoped followed-stores endpoint. | Follow/unfollow actions are available from store details; no followed-store list is shown. |
| Store review moderation | Public review listing and submission exist; moderation is an administrative operation. | Use the existing platform-admin workflow; no additional client endpoint is needed. | Clients can list and submit product/store reviews; submitted reviews may require moderation. |
| Analytics | Store dashboard data is available only where the backend returns it and depends on real store activity. | No frontend substitute; populate through actual platform transactions. | Displays API results or an empty-data message, never invented metrics. |
| Payment processing | Store payment history can be read, but this repository has no configured provider checkout, verified webhook, or refund processing. | Choose and configure a payment provider, verify webhook signatures, and implement provider-backed refund workflows before representing payments as settled. | Transactions are read-only and use actual stored payment/refund rows. |
| Audit coverage | Store audit history, append-only protection, inventory snapshots, membership/store/order/listing mutation events exist; some unrelated social, appointment, notification, and platform mutations are not part of the store journal. | Extend audit events transactionally when those mutations become part of the shop-owner workflow. | History is paginated, searchable, and server-backed; legacy rows cannot be given retroactive snapshots. |
| Shop configuration | Existing model supports core contact/branding/timezone/currency fields but does not model opening hours or social links. | Add reviewed schema/API support if those fields become requirements. | Only fields supported by the existing store model are editable. |
| Reporting extras | Global search, export, automated low-stock notifications, and custom employee permission matrices are not available. | Implement audited, authorized backend APIs before exposing these capabilities. | Not represented as working features. |

Store/member/inventory authorization remains enforced by the API. Choosing the optician workspace is a navigation preference, not a security role.
